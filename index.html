Chapter 1

The bank server stays exactly the same: OBDX on WebLogic, Flexcube behind it, and NBE's custom cz/… services. What changes is the app the customer holds. The old one is web pages inside a Cordova shell. The new one is a real Flutter app that draws screens from JSON files.

Chapter 4

Flutter and Dart in five minutes

In one lineDart is the language, Flutter draws the screens, and SDUI means screens are written as JSON.

Dart

The programming language. Looks like Java/TypeScript. Files end in .dart. It plays the role JavaScript played in the old channel.

Flutter

Google's UI framework written in Dart. One codebase builds Android, iOS and Web. It plays the role of Oracle JET.

Widget

Everything on screen is a widget: Text, Row, Column, Button. Widgets nest inside each other like HTML tags. A widget is like a JET oj-* element.

Riverpod

Holds app state and shares it between screens (the "providers"). Plays the role of Knockout observables plus baseModel.

GoRouter

Navigation by URL path, like /accounts or /sdui/iscore/iscore_inquiry. Replaces dashboard.loadComponent.

Dio

The HTTP client. Plays the role of baseService.fetch / add, with interceptors for nonce, cookies, 2FA and errors.

The big twist: SDUI. In a normal Flutter app, every screen is a Dart file. This team built a Server-Driven UI engine instead: screens are JSON files, and Dart code reads the JSON and builds the widgets. So most of your daily work is JSON, not Dart.

Chapter 6

Each old file, one by one, and what replaced it

In one lineOld: each screen carries its own loader, JS, hooks, model, HTML and styles. New: the screen is one JSON file, and the shared engine does the rest.

Real example: the old i-score-inquiry folder against the new iscore_inquiry.json.

loader.jsold
Old job
Tells RequireJS which files make up the component: the HTML template, the viewModel and the CSS. It glues them together so Knockout can show it.
Now
No file per screen. The route plus SDUIScreenLoader('iscore/iscore_inquiry') finds and loads the JSON.
Difference
You never write a loader. Naming the file correctly (its id = its path) is enough.
i-score-inquiry.jsviewModel
Old job
The brain of the screen: creates Knockout observables, reads params, validates, handles button clicks, calls the model, switches stage CREATE → REVIEW.
Now
Split in two. Values go in "state". Click logic goes in "action" blocks (setState, conditional, navigate, api). Each step runs as a shared Dart plugin.
Difference
No JavaScript to write. Rules like "EGP only" become a conditional action. Review becomes its own screen instead of a stage flag.
hooks.jsold
Old job
Found in components generated by Oracle's UI Workbench (e.g. i-score-view). Holds the API wrapper calls and event hooks such as SelectPeriod50ValueChangeHook, so custom logic stays outside the generated viewModel.
Now
Event hooks become onChanged actions on the widget (dropdown, date field, text field). API wrappers become api actions.
Difference
The "react when a value changes" logic sits right on the field in JSON, not in a separate file.
model.jsold
Old job
Defines each API call: URL, version, method, params, and returns a jQuery Deferred. Uses baseService.fetch / add / update / remove / downloadFile.
Now
"page.api.onLoad" for calls when the screen opens; an "api" or "downloadFile" action for calls on tap. The response is saved as $data.<id>.
Difference
Same URLs and payloads. Keep the old model.js open while you build: it's your API contract, including task codes and field names.
i-score-inquiry.htmlold
Old job
Markup with JET tags (oj-button, oj-select-one) and shared elements (account-input, page-section), bound with data-bind.
Now
The "layout" tree in JSON: Column, Text, Button, DropdownComponent…
Difference
No bindings syntax. Write "text": "$state.x" and the widget updates itself when the value changes.
.scss / .cssold
Old job
Per-component styles plus JET classes like oj-flex oj-sm-12 for layout.
Now
Inline style names from the theme: "style": {"typography": "labelSmall", "color": "primary"}, spacing tokens, Row/Column for layout.
Difference
No stylesheet per screen. Change apptheme.json once and every screen follows.
.json / component.jsonold
Old job
Component metadata. Empty for most screens (the iScore ones are 0 bytes). For shared elements like account-input, component.json lists the properties it accepts.
Now
The screen JSON is the screen. Widget properties are read by the Dart widget builder (e.g. sdui_dropdown_component.dart).
Difference
Old JSON described a component; new JSON is the whole screen.
nls/*.jsold
Old job
Labels per component, in resources/nls/ (English) and nls/ar/ (Arabic).
Now
One shared file per language: common/translations/en.json and ar.json. Prefix keys with the feature: iscore….
Difference
Copy the Arabic text straight from the old nls file.

Chapter 8

What happens when the app opens

In one linemain.dart picks the environment, bootstrap.dart prepares everything, then the login screen opens.

In OBDX, index.html loads require-config.js, then the framework, then the dashboard. In Flutter, it's main.dart → bootstrap.dart. These steps run in this exact order:

Show details
  1. Pick the environmentmain.dart (dev), main_sit.dart, main_uat.dart or main_prod.dart calls FlavorConfig.initialize(): base URL, logging, security switches.
  2. Security firstStarts the AES helper, prepares SSL pinning, and runs the root/jailbreak check. A compromised phone gets the block screen and stops here.
  3. Open local storageHive boxes for cached screen JSON, HTML and schema versions; SharedPreferences; secure storage is wiped on first run.
  4. FirebaseAnalytics only (no push messaging in this app yet).
  5. Prime the SDUI engineLoads the asset list, registers all validation rules, and registers every action plugin into the SduiActionDispatcher.
  6. SessionMobile clears any old session (fresh login every launch). Web tries to resume the existing cookie session.
  7. Pre-login permissionsFetches which components are allowed before login (me/components).
  8. Run the apprunApp(BankingApp) → GoRouter shows the login screen, which is itself the SDUI file mobile/auth/login.json.

Chapter 10

Anatomy of a screen JSON file

In one lineEvery screen file has the same 5 parts: id, state, page, actions, layout.

Here's a shortened version of the iScore review screen. Every screen has the same top-level shape.

{
  "id": "mobile/iscore/iscore_review",  1
  "version": 1,
  "state": { "accepted": false },           2
  "page": {                                    3
    "type": "screen",                         // or "bottomSheet"
    "api": { "onLoad": [ { "id": "accountsData", "method": "GET",
              "url": "/digx/v1/accounts/demandDeposit?taskCode=PC_F_ISC" } ] },  4
    "appBar": { "type": "AppBar", "title": { "type": "Text", "text": "review" } },
    "bottomNavigationBar": {
      "type": "Button", "label": "confirm",          5
      "action": {                                 6
        "type": "api", "id": "iscoreRequest", "method": "POST",
        "url": "/digx/v1/cz/iscore",
        "body": { "language": "$data.language" },      7
        "onSuccess": { "type": "navigate",
          "route": "/sdui/iscore/iscore_success",
          "argument": { "ref": "$data.iscoreRequest.iscoreDTO.id" } }
      }
    }
  },
  "layout": {                                  8
    "type": "Column", "children": [
      { "type": "Text", "text": "iscoreLanguage" },
      { "type": "Text", "text": "$data.languageDesc" }
    ]
  }
}
  1. id must equal the file path without .json. The loader uses it to find the file.
  2. state holds the starting values for this screen's $state. Like declaring ko.observable(false) in a viewModel.
  3. page holds the screen frame: type, app bar, bottom bar, API calls. Bottom sheets use "type": "bottomSheet".
  4. page.api.onLoad runs when the screen opens. Each response is saved as $data.<id>, so this one becomes $data.accountsData. This replaces model.js.
  5. Labels are translation keys. "confirm" is looked up in en.json/ar.json. Text starting with $ is a value, not a key.
  6. action says what a tap does. Here, an api action calls OBDX. Actions can chain through onSuccess, composite and conditional.
  7. Expressions like $data.language are filled in at run time (chapter 11).
  8. layout is the widget tree, nested like HTML. Every "type" must exist in the widget registry (chapter 13).
Chapter 11

Where values live: $state, $data and friends

In one line$state is what the user picks. $data is what the server returns or the last screen sent.

Think of these as the observables of the old viewModel, with fixed names.

Write thisIt meansOld OBDX equivalent
$state.xWhat the user picked or typed on this screen. Changed by setState, inputs and dropdowns.self.x = ko.observable()
$data.xAPI responses (by their id) plus the argument sent by the previous screen.params.rootModel + model responses
$item, $indexThe current row inside a ListViewBuilder or ForEach.$data inside foreach binding
$localeen or ar.baseModel.getLocale()
$tokens.spacing.mA design token value (16).SCSS variable
$config.baseUrlValues from FlavorConfig.Configurations
${ … }A full expression: ${$state.a == true && $state.b != ''}Knockout pureComputed

Useful helpers inside expressions: .length, .first, .last, .find('field', value), .anyMatch('field', value), .formatCurrency, .toUpperCase, .substring, and ternary a ? b : c.

Sheets share the parent's values. A bottom sheet opened with openOverlay reads and writes the parent screen's $state and $data. That's how the account sheet sets fromAccountDTO and the form sees it right away.

Chapter 14

In one lineNo CSS files. Use names like "primary" and "labelSmall" from one theme file.

There are no per-screen stylesheets. Colors, type and spacing come from one file, sdui_assets/common/theme/apptheme.json, and screens refer to them by name.

SDUI
Server-Driven UI. Screens are JSON files that a Dart engine turns into widgets. Today the JSON ships inside the app; later it can come from the server without an app update.
screenId
The JSON path without .json, e.g. mobile/iscore/iscore_inquiry.
Flavor
An environment build: dev, sit, uat, prod. Each has its own main_*.dart and settings in flavor_config.dart.
Widget registry
The list that maps a JSON "type" to Dart code that draws it.
Action plugin
Dart class that runs one action type (api, navigate…).
Orchestrator
Prepares a screen: resets state, merges incoming data, runs onLoad APIs.
Overlay
A bottom sheet or dialog. Shares its parent screen's state.
Provider
A Riverpod object that holds state; widgets that read it redraw when it changes.
Interceptor
A Dio hook that runs on every request/response (nonce, cookies, 2FA, errors).
Hive
Small local database on the phone; caches screen JSON and HTML.
pubspec.yaml
The project file: packages, fonts, asset folders. Like package.json plus the asset list.
Hot reload / restart
Reload keeps state and won't pick up new JSON; restart reloads everything. Use restart for SDUI changes.
fvm
Flutter Version Manager; .fvmrc pins this project to 3.32.6.
